## Update System Audit (2026-10-13 Asia/Hong_Kong)

- The update primitives are present and guarded, but the requested guarantee is not yet met for every deployed instance. The latest formal GitHub Release is still `v0.3.0`; `https://artichatupdate.artivis.cc/index.json` responds `200` with the 0.3.1 announcement, while the public `chat.artivis.cc` `/health`, `/ready`, and `/api/version` endpoints currently respond `502`. No production host or data was changed.
- Version detection is a pull performed when an administrator opens or refreshes `设置 -> 更新`. The old global `UpdateInfoToast` was intentionally removed in 0.1.5 and remains absent from the application layout. Therefore a deployed 0.3.0 instance does not proactively push a release notice to all users; an administrator must open the update page, or an external notification channel must be added.
- One-click deployment is available only for an instance with `ARTICHAT_UPDATE_GITHUB_TOKEN`, a matching `ARTICHAT_UPDATE_REPOSITORY`/workflow/ref, the persistent update-state mount, and the restricted SSH runner plus GitHub Actions production secrets. The local 3003 preview has no deployment token; its update endpoints return `401` without an administrator session. The deployment button is correctly hidden when the token is absent.
- The default repository `PYBu/ArtiChat` and its workflow target the maintained deployment server. A self-hosted installation cannot safely use that default for its own one-click update: each independent deployment needs its own repository/workflow, GHCR image repository, restricted runner, host-key secret, and token with Actions write permission. A central release cannot push arbitrary updates into unrelated installations.
- Verification completed in this audit: `npm run test:updates` passed; `npx vitest run src/lib/utils/updates.test.ts` passed 3 tests; the prior isolated deployment harness passed upgrade, rollback, rollback-failure, repository-derivation, and external-persistence refusal cases; 3003 anonymous checks returned `401` for update check/status/announcement and legacy version-update routes. The Linux Bash harness is not runnable directly on this Windows host (`/bin/bash` is unavailable), so no new host mutation was attempted.
- Decision: publish the 0.3.1 release as authorized above, while keeping production deployment separate. For the maintained server, provision and verify its token/runner before any real dispatch. For all self-hosted users, first implement and document per-instance onboarding plus an external notification path; current code supports admin pull and configured one-click deployment, not universal push.

### Flow Clarification (2026-09-26)

- Re-traced the current source rather than relying on the earlier summary. In native function calling, `process_chat_payload` exposes media tools only when the request is non-legacy and the global feature, model capability, builtin category, and user permission gates pass. The model streams a tool call; the middleware executes it, appends a tool result, emits the updated tool-call output, and starts a fresh model continuation. The loop can repeat until no tool call remains.
- Image tool result: `generate_image` waits for provider completion, persists chat message files, emits `chat:message:files`, and returns one JSON result containing `status`, `images`, and each image `id`/`url`. The model continuation receives that JSON result; the browser receives the file event.
- Video tool result: `generate_video` creates a durable job and waits for a terminal row. The worker downloads and persists the MP4, attaches it to the chat, emits the `files` event with the local URL, and only then allows the waiter to observe success. The model continuation receives JSON with `status`, `job_id`, `file_id`, and a message, but no video URL. Therefore there is one tool execution with two output channels, not a first success return followed by a second URL return.
- Failure result: native image/video exceptions are converted into structured JSON error text for the model continuation. Legacy function calling is a separate path: it runs the image/video middleware before the main model completion, emits files/status events, and injects a success/failure system context; it does not provide a native tool result to the model.
- Optimization decision remains open: either keep the UI-first video attachment contract and add a canonical local URL to the video tool result, or unify legacy media generation with the native tool-call loop. Do not change the native image/video ordering until this product behavior is selected.

- Rechecked the full chat path against the user's observed sequence. With native function calling, the model can stream reasoning and a `generate_image`/`generate_video` call first; the middleware executes the tool, appends its result, and only then starts the model continuation request.
- Native image generation is synchronous. `image_generations` waits for provider output, stores the image in an ArtiChat file, and returns a local URL. `generate_image` persists the message file and emits `chat:message:files` before returning the success result. An error is returned as a structured tool result, so the model receives it and produces the error reply.

Failure and timeout results likewise go back to the model for the final reply.

It does not expose the same model-generated native tool-call sequence, although it also waits for the media job before the final model response.
