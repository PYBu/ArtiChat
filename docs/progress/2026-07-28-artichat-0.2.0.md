## Chatpoint Accounting And Reservation Safety

- Migration head `f5a6b7c8d9e0` adds durable `subscription_reservation` state, subscription balance versions, usage reservation identity, unpaid-cost audit fields, and required unique indexes. The migration can recreate an empty partial reservation table, repairs missing indexes on rerun, and refuses to drop a populated partial table.
- Reservations debit Plan before Check atomically and never allow negative balances. Settlement, release, expiry, usage insertion, balance mutation, and ledger insertion share a transaction in the covered paths.
- Provider calls reserve estimated input plus a capped output allowance immediately before dispatch. Every tool/provider continuation extends the same reservation before it can call the provider.
- Output limits cover `max_tokens`, `max_completion_tokens`, `max_output_tokens`, `options.num_predict`, and `options.max_tokens`; conflicting aliases are all clamped to the safest value. The final Ollama adapter now preserves nested root options and maps the reserved limit to `options.num_predict` without allowing a larger alias to win.
- Missing, unknown, or all-zero provider usage fails closed to the held amount after content was delivered. Total-only usage and unclassified token deltas are charged conservatively at the highest applicable token price. Usage rows are idempotent by reservation identity, so two models sharing a parent request cannot collide.
- Active reservations have renewable leases and a periodic production cleanup loop. A transient heartbeat database error is retried rather than permanently ending lease renewal.
- Period reset and automatic downgrade now update the subscription and matching ledger in one transaction. Fault-injection tests prove both roll back if ledger insertion fails. Terminal `release(..., commit=False)` no longer commits its caller's transaction.
- Multi-model processing resolves Arena children before reservation, reserves the complete raw batch, prepares targets concurrently, atomically reconciles all final payload holds, and holds provider tasks behind a dispatch gate until registration and reconciliation succeed. Failure cancels and gathers local tasks, releases all holds, and dispatches no intentional subset. Initial title generation is deferred until the main fanout succeeds.
- A dynamic lifecycle test extracts and runs the nested worker, proving preparation and dispatch gates, prepared-future timing, and same-task MCP connect/disconnect behavior rather than relying only on source ordering.

### Business Semantics Audit

- Redemption codes need an explicit `benefit_type = subscription | recharge | legacy`; type must never be inferred from a loose field combination. Existing copied-volume codes are mixed historical benefits and must migrate to `legacy` without changing redeemability.
- New subscription cards contain plan plus duration only. New recharge cards add recharge/Check Chatpoints only. Gift grants inherit the linked code type rather than duplicating it.
- The visible Disable action must preserve code hash and identity while setting `is_active=false`. The existing DELETE behavior mutates the hash and is unsuitable.
- Recommended bulk clear semantics are an invisible tombstone (`purged_at`) that clears displayable plaintext/memo while retaining hash, IDs, and audit relationships. Physical deletion would orphan audit rows and permit old codes to be reissued.
- Server-side status classification must distinguish available, used, disabled, expired, and purged; lists need pagination and counts. The final-use path also needs an atomic conditional update to prevent concurrent over-redemption.
- Recommended lower-tier subscription behavior is reject without consuming the card. Existing behavior can consume a code while silently declining the downgrade.
- Announcement DELETE must transactionally delete related view rows and the announcement. Enable/disable remains a separate PATCH switch. Existing inactive announcements cannot be auto-classified as prior deletes versus deliberate disables, so migration must preserve them for manual review.
- The existing billing data already owns all four token classes and Plan/Check costs. The redesigned ledger should extend its filters/pagination and correct redemption net deltas, not create a second accounting source.
