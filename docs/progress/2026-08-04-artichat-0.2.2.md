## 0.2.2 Chat Settlement Product Decisions (2026-08-04)

- Approved direction: split provider completion from Chatpoint settlement so a completed model response can release the next prompt without waiting for billing persistence.
- Do not show a user-facing “费用结算中” or equivalent status. Settlement state remains internal and is observable through durable records/logs only.
- Add a defense against unbounded pending settlements. The exact per-user/per-chat/system threshold and recovery behavior are still to be designed; the guard must not hard-block a prompt merely because a previous response is still settling.
- If a user has no remaining quota when a pending settlement finishes, allow that already-started usage to settle according to the accounting policy, then block subsequent questions through the normal balance guard. Do not retroactively cancel a provider response solely because the balance became empty during settlement.
- The visible upper-right no-quota copy should become `额度不足支撑下次对话。`.
- Preserve the model/provider error contract exactly: insufficient input balance continues to return `CHATPOINT_BALANCE_INSUFFICIENT_FOR_INPUT`.
- Required implementation gates before changing production semantics: durable settlement job/outbox, reservation/request idempotency, retry and restart recovery, pending-settlement accumulation tests, concurrent next-prompt tests, and negative-balance/insufficient-after-settlement tests.
- No code changes for this decision have been made yet; it remains the next approved exploration/implementation scope.

## 0.2.2 Approved Problem-Solution Decisions (2026-08-04)

### Email delivery latency

- Approved solution: use the existing `EmailDeliveries` records as a durable outbox. The challenge request creates the challenge and queued delivery atomically, returns quickly, and lets a worker perform the existing SMTP/template flow asynchronously.
- The frontend opens the verification-code input promptly after queue acceptance. It must distinguish queued/sent/failed internally so it does not claim delivery success for a failed task; verification must not succeed while the delivery task is still pending.
- The worker needs leases, bounded retry/backoff, restart recovery, and idempotent delivery state. FastAPI process-local background tasks alone are not sufficient.
- SMTP connection reuse and transport tuning are secondary optimizations after the durable request/worker path is in place. No implementation has started for this decision yet.

### Chat completion and Chatpoint settlement

- Approved solution: split provider completion from billing settlement. Persist the completed response and a durable settlement task, emit completion, and allow the next prompt without waiting for the settlement transaction.
- Do not show a user-facing settlement indicator. Internal settlement state remains available for operations and recovery only.
- Use a soft grace period with a hard pending-settlement cap. Every new request still requires a reservation; the system must account for active holds and reject only after the configured cap or actual available balance is exhausted.
- If settlement later finds the quota exhausted, finish accounting for the already-started response according to the partial/unpaid policy, then block subsequent prompts. Do not cancel the completed provider response retroactively.
- Keep the model error code `CHATPOINT_BALANCE_INSUFFICIENT_FOR_INPUT` unchanged. Change the upper-right no-quota copy to `额度不足支撑下次对话。`.
- Required tests: concurrent next prompts, cap enforcement, worker restart/retry, duplicate settlement, insufficient-after-settlement, no-negative-balance, and future-prompt blocking. No implementation has started for this decision yet.
## 0.2.2 Implemented Latency Fixes (2026-08-05)

- Email challenges now use `enqueue_email` and the existing `email_delivery` table as a durable outbox. The request returns after the encrypted rendered payload is persisted, so the verification-code input can open without waiting for SMTP. The scheduler retries pending/failed rows with bounded exponential backoff and reclaims stale `sending` rows after a lease. The plaintext code is not stored; the queued rendered payload is encrypted with a key derived from `WEBUI_SECRET_KEY`.
- The challenge response now includes `delivery_id` and `delivery_status: pending`; queue creation failures invalidate the challenge and return `EMAIL_DELIVERY_FAILED`. Existing synchronous password/account notification flows and admin retry behavior remain unchanged.
- Chat completion now defers Chatpoint settlement when a reservation exists. It refunds the input hold immediately, stores the complete billing payload in reservation metadata, emits the provider-complete response, and lets the next prompt reserve normally. A scheduler worker claims and settles the durable record with the existing reservation/idempotency path; retries are lease-based and duplicate settlement is terminal/idempotent.
- Pending settlements are capped at three per user. When the cap is reached, the current request uses the existing synchronous settlement path instead of accumulating more durable tasks. If a deferred settlement has no remaining quota, the existing partial/unpaid accounting records the shortfall; future input still reaches the normal balance guard.
- The upper-right quota toast maps only `CHATPOINT_BALANCE_EXHAUSTED` to `额度不足支撑下次对话。`; provider/model `CHATPOINT_BALANCE_INSUFFICIENT_FOR_INPUT` remains unchanged.
- The sidebar quota ring now routes desktop and mobile clicks directly to `/account/subscription?tab=usage` instead of only opening an in-modal tab or mobile detail popover.

## Mailbox Tool Brainstorm (Not Implemented)

- Keep the model mailbox separate from verification SMTP: separate config namespace, sender identity, encrypted credential, rate limits, audit records, and worker queue. Admin Settings -> Extensions should expose only an enable switch until enabled; disabled means no model tool or SMTP settings are visible.
- The tool must derive the recipient from the authenticated user's current registered email on the server. The model may supply subject/body and an automation schedule, but it must never choose an arbitrary recipient, add CC/BCC, or override the registered address.
- Add explicit send intent/confirmation for one-off sends and a separate consent flow for recurring automations. Enforce per-user daily/hourly limits, message-size/attachment restrictions, idempotency keys, retry/backoff, and an audit trail without storing SMTP secrets in prompts or task payloads.
- Automation jobs should enqueue a durable mail task and report delivery status internally. Use a dedicated tool permission and sender display name so this feature cannot silently reuse verification-mail credentials. This remains architecture discussion only for a later update.

## 0.2.2 Billing UI Investigation (2026-08-05)

- No source implementation was changed during this investigation.
- The personal Settings modal uses one shared body wrapper (`flex-1 min-h-0 overflow-hidden`), but the Billing tabs do not follow the same page structure as the other settings tabs. `Subscription.svelte` makes its title an inline row child and puts the whole page on `overflow-y-auto`; `UsageCenter.svelte` has a title row with its own control group; and `RedeemCode.svelte` places its title inside an `mx-auto max-w-2xl` wrapper. The resulting title alignment and scroll ownership differ from the standard left-aligned `h2` plus separate scroll-content pattern used by Account/General/About.
- The standalone quota-ring route renders `SubscriptionCenter.svelte`, whose header is outside the child pages, while Subscription, SubscriptionUsage, and RedeemCode each use different root widths and scrollbar behavior. RedeemCode centers its whole content column; the other two fill the parent. Switching tabs can therefore change scrollbar/centering geometry and make the page appear to shift horizontally. The header itself is also coupled to the centered `mx-auto max-w-6xl` page shell rather than a stable left-anchored content frame.
- The Subscription Center tab state has a confirmed URL-sync race. `selectTab` assigns `tab` and then calls `goto`; before the URL changes, the reactive block at lines 21-24 reads the old `$page.url.searchParams.get('tab')` and can overwrite the new local tab. Clicking Overview from `?tab=usage` deletes the query parameter, so the stale `usage` value can briefly or persistently win, causing the observed URL clearing, failure to open Subscription, and tab flicker.
- Proposed discussion scope before implementation: standardize all three personal Billing pages on the existing settings title/scroll grammar; give standalone Subscription Center one stable left-aligned header/content frame and one consistent scroll owner; then make URL state authoritative without allowing stale route parameters to overwrite an in-flight tab selection.
