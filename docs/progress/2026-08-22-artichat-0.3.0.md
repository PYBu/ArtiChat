## Billing Architecture Review (2026-08-22)

### Confirmed Findings

- **Critical: the configurable continuation limit is not an atomic limit.** `bill_subscription_usage_once` counts pending reservations and then defers a separate reservation. Concurrent completions can all observe the same count before any of them commits, exceed the configured allowance, refund multiple holds, and create additional unpaid overage. The limit is currently advisory rather than a concurrency-safe quota.
- **High: pending settlements can be starved.** The queue marker is stored in reservation JSON metadata. `list_pending_chatpoint_settlements` reads the oldest active reservations, scans only `limit * 4` rows, and filters the marker in Python. A group of long-running non-pending reservations can keep newer pending settlements out of the worker window.
- **High: a deferred settlement can be lost after 24 hours.** Deferral changes the active reservation expiry to `now + 86400`; the independent expired-reservation cleanup can then terminally expire that row while its pending marker is still waiting. The settlement worker ignores terminal rows, so no usage row or final charge is produced.
- **Medium: settlement has avoidable database work.** `bill_model_usage` calls `ensure_subscription_current`, then `settle_chatpoint_reservation` repeats subscription refresh/locking, and `adjust_balances` locks and reads the subscription again before writing the ledger. The synchronous fallback therefore holds the request open across several redundant reads, writes, and lock operations.
- **Medium: queue throughput and recovery are coupled to the unified in-process scheduler.** Settlement is processed serially in batches of 10 alongside SMTP, automation, and calendar work. Claims use a 120-second lease, but retries have no `next_attempt_at`, exponential backoff, maximum-attempt/dead-letter state, or oldest-queue-age metric. The scheduler task is also not retained for explicit shutdown cancellation.
- **Medium: there is no settlement latency telemetry.** Only synchronous billing logs when it exceeds 500 ms; deferred queue age, claim wait, settlement duration, retry count, and pending depth are not measured, so capacity decisions are currently guesswork.

### Rewrite Decision

- Do **not** replace the billing system wholesale in 0.3.0. The reservation, usage, ledger, idempotency, partial-settlement, and cross-period invariants are valuable and already covered by focused tests; a rewrite would create a large data-migration and double-charge risk.
- Prefer an incremental settlement refactor: retain existing reservation/usage/ledger tables and public helpers, add a durable indexed settlement-job state (or equivalent reservation columns), claim jobs with database ordering/locking, and make expired-reservation cleanup skip queued jobs.
- Consolidate settlement into one caller-owned transaction that locks the subscription and reservation in one consistent order, writes the balance/ledger/reservation/usage result once, and avoids repeated `ensure_subscription_current` and `adjust_balances` lookups.
- Add a local wake-up event plus timer fallback, bounded worker concurrency, retry backoff/dead-letter handling, and queue-age/duration metrics. Keep synchronous settlement as the safety fallback while the queue is unavailable.

### Security And Feasibility Audit

- The first phase must atomically allocate a per-user continuation slot while holding the user subscription row (or an equivalent user-scoped counter/job row). A read-then-enqueue check is not sufficient. The reservation and slot/job transition must commit together, and the slot must be released exactly once on successful settlement or terminal release.
- A separate settlement-job table is feasible across the supported SQLite/PostgreSQL/MariaDB paths, but claims must use a dialect-neutral compare-and-swap/lease update. `SKIP LOCKED` can be an optional PostgreSQL/MariaDB optimization, never the correctness requirement. The migration must be additive and preserve the legacy metadata reader during rollout and rollback.
- Workers must derive `user_id`, `model_id`, `request_id`, billing policy, and admin/bypass state from the reservation or an immutable server-side snapshot. Do not trust mutable job payload identity or an `is_admin` flag. Keep the job payload minimal, size-bounded, and free of prompts, provider credentials, headers, or raw authenticated requests; sanitize retry errors before persistence/logging.
- Retry backoff, a maximum attempt count, and a dead-letter/manual-reconciliation state are security controls against an invalid payload or provider/database failure becoming an endless write/lock loop. Any admin inspection or replay endpoint must be admin-only and must not permit arbitrary balance mutations.
- The local wake-up event is only a latency optimization. Correctness must continue to work with timer polling because an asyncio event is process-local and Redis is optional. The worker task must be retained and cancelled/awaited during lifespan shutdown.
- A full external billing service is not justified yet: it would add credentials, network, deployment, reconciliation, and cross-service failure surfaces before the local invariants are corrected.

### Recommended Sequence

1. Correctness first: prevent pending-job expiry/loss and add a regression test for worker downtime beyond the current 24-hour reservation expiry.
2. Observability: record `queued_at`, `started_at`, `settled_at`, attempts, oldest pending age, and sync-fallback rate.
3. Performance: implement the single-transaction settlement service, indexed job claiming, and controlled concurrency; benchmark p50/p95 completion latency before and after.
4. Reconsider a broader rewrite only if production measurements show the incremental design cannot meet the required throughput.
